# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

t1ld3 (formerly Resonance) is a desktop hub for Windows and Linux, built with customtkinter and spotipy. It has a command launcher, a today briefing, now playing, weather, a to-do list, a calendar and accounts with sync, plus an always-on-top Spotify player that pops out. It has day and night themes. The display name lives in `APP_NAME` in `constants.py`. The Python package (`resonance/`), the class names and the GitHub repo still use the old name.

## Commands

```bash
python3 -m venv .venv && source .venv/bin/activate
python -m pip install -r requirements.txt
python main.py
```

Runtime dependencies are in `requirements.txt`. There's no test suite or linter config yet; `python -m pyflakes resonance/ main.py` catches unused imports and undefined names.

Local PyInstaller build (mirrors CI; on Windows use `;` instead of `:` in `--add-data` and add `--icon=assets\icon.ico`):

```bash
pyinstaller --clean --onefile --windowed --name t1ld3-linux \
  --add-data "assets/terminal_theme.json:assets" --add-data "assets/icon.ico:assets" \
  --add-data "assets/quotes.json:assets" \
  --collect-submodules resonance.apps \
  main.py
```

Spotify sign-in uses PKCE, so there's no client secret. The app's client ID (`SPOTIFY_CLIENT_ID` in `constants.py`) is public by design. Each user signs in once per device in the browser, and the token is cached in `<data folder>/spotify-token.json`. Users must be added under User Management in the Spotify dashboard (Development mode). For testing against another Spotify app, set the `SPOTIPY_CLIENT_ID` and `SPOTIPY_REDIRECT_URI` environment variables. Playback controls need Spotify Premium.

## Architecture

- **Startup order matters.** `main.py` first calls `instance.notify_running_instance()`, then `paths.prepare_data_dir()`, which creates the data folder (`$LOCALAPPDATA/t1ld3`, or `~/t1ld3` on Linux) and moves a pre-rename `Resonance` folder across. Only afterwards is `app` imported, because importing `backend` creates the module-level `spotify` client, whose token cache lives in that folder.
- **`backend.py`** is a thin, synchronous wrapper over spotipy (`get_current_song()` normalizes playback state into a flat dict; play/pause/seek/volume helpers) plus refresh-interval constants.
- **`app.py`** holds `ResonanceApp(customtkinter.CTk)`, a *hidden* root window that owns the shared state: the worker pool, Spotify polling (`poll_song` → `refresh_song`), the current song, and the dithered album art. It pushes results to every open window through `show_song(song)`, `show_song_error()` and `set_album_art(images)` (a `(day, night)` pair), and it handles playback actions. The root stays hidden because Tk closes every window when the root is destroyed. That is what lets the hub close while the player stays open. The app quits once both windows are closed (`quit_if_no_windows`).
- **`hub.py`** holds `HubWindow` (the main window, opened at startup) and **`player.py`** holds `PlayerWindow` (the always-on-top player that pops out from the hub). Both are `CTkToplevel`s that implement the three window methods above. Close a window through `app.close_hub()`/`app.close_player()`, not `destroy()` directly. Bind keys on the window with `self.bind`, never `bind_all`, which would leak into the other window.
- **Threading:** blocking work (Spotify API calls, album-art downloads, update checks) goes to `app.worker`, a `ThreadPoolExecutor(max_workers=4)`. The first Spotify login holds one worker until it's approved in the browser. Each request uses a `*_finished(future)` callback that hops back to the Tk thread with `self.after(0, self.apply_*, future)`. Follow this pattern; never touch widgets from worker threads. Polling loops (`update_time`, `update_progress`, `update_quote`, and the `NoiseBand`/`Starfield` twinkles) reschedule themselves with `self.after`. Each widget that owns a loop calls `windows.cancel_pending_after(self)` in `destroy()`, so the loops stop with it. That helper must never raise, or the window can't close.
- **`windows.py`** holds per-window helpers: the Windows icon and taskbar fix (`prepare_window`), `outline_width` (CTk scales border widths, so 1px borders vanish below 100%), and `cancel_pending_after`.
- **`ascii_art.py`** renders album art as dithered ASCII glyphs with the orange pixel figure, and makes the noise text. `noise_band.py` (rows of flickering noise) and `starfield.py` (a canvas of twinkling stars that fills empty space) decorate the windows. The visual language is a bone background, ink text, monospace type, square corners and orange as the only accent. Use the palette and `MONO_FONT` from `constants.py`.
- **Day/night themes (`theme.py`):** every palette constant is a `(day, night)` pair. CTk widgets take the pairs directly and repaint when `theme.set_night()` switches customtkinter's appearance mode. Anything that isn't a CTk widget must resolve colours with `theme.color()` at draw time and register a redraw with `theme.watch()`/`unwatch()`: the canvases (calendar, `Starfield`), plain `tk.Frame`s (`windows.add_rule`), and colours computed by hand (the player's loading fade). Pillow art is rendered as a `(day, night)` pair with `ascii_art.both_themes()` and shown through `CTkImage(light_image, dark_image)`. At night, photos map brightness to density (with a gamma and a cap, to stay sparse) so they don't come out as negatives. The figure keeps fixed colours (`FIGURE_COLOR`/`FIGURE_SHADE`). Never use a bare palette constant where Tk or Pillow expects a string. The app picks night from the synced `theme` setting (`auto`/`night`/`day`), and in auto from the forecast's sunrise and sunset (falling back to 7am–7pm), checking every minute. `assets/terminal_theme.json` holds the night colours as the second value of each pair.
- **Battery:** `battery.py` reads the system battery with the standard library only (`/sys/class/power_supply` on Linux, skipping `scope=Device` batteries in peripherals; `GetSystemPowerStatus` on Windows) and returns None without one. The hub header shows it only when it's present, refreshing every 30s.
- **Event reminders:** each event has a `remind` lead time in minutes (`0` = at the start, `None` = off, missing = `DEFAULT_REMIND`, 10), chosen in the event dialog. All-day events don't remind. `reminders.py` holds the timing, with no UI code: `due_reminders` returns timed events whose reminder time has passed, still allowing up to `LATE_GRACE` after the start for a sleeping or late-started app. The app checks every 20s (`check_reminders`). `notify.py` sends a system notification from a worker (`notify-send` on Linux; a PowerShell toast on Windows, with the text passed in environment variables). If that fails, `toast.Toast` shows a borderless note in the screen's corner. Sent reminders are kept per device in `device.json` (`reminders_sent`, keyed by day, id, start and lead time, so a moved event reminds again), and older days are pruned. Reminders only fire while the app is running.
- **Today briefing:** `today_panel.py` reads to-dos, events and `app.weather` (which the weather panel publishes through `app.weather_updated`). It refreshes on local edits (as a collection listener), on `data_changed` and every minute.
- **Weather:** `weather.py` holds the blocking API calls: `locate_by_ip` (ipinfo.io), `search_city` (Open-Meteo geocoding) and `get_weather` (Open-Meteo forecast, no API key). `weather_panel.py` holds the hub panel, which asks before using the user's IP address. Its worker requests carry a `request_id`, so only the newest result updates the panel.
- **`settings.py`**: synced preferences (a collection in `settings.json`) plus device-only ones (`device.json`). The weather keys are `share_location` (True means look up by IP on each launch, False means use the saved city, missing means ask) and `weather_location`.
- **Launcher:** `launcher.py` contains no UI code. It loads `commands.json` (in the data folder, written with per-OS defaults on first run), and it handles matching and suggestions (`suggest`), the `{args}`/`{query}`/`~` expansion, starting detached processes (`run_command`) and a safe arithmetic evaluator (`calculate`, AST-based, never `eval`). `launcher_panel.py` holds the hub prompt, and passes the hub's app names to `suggest` as `pages`. Its suggestion dropdown is a child of the hub, placed over the panels below it, and it reuses a fixed set of `MAX_SUGGESTIONS` rows, because creating CTk widgets on every keystroke lags. The built-ins (`player`, `play <song>`, `todo <task>`, `phone <note>` (pushed to the phone app), `cal`, `home`, `account`, `theme`, `quit`) are handled in the panel.
- **Single instance:** `instance.py` listens on `127.0.0.1:47917`. `main.py` calls `notify_running_instance()` before anything else, so a second launch just asks the running copy to show its hub, then exits. A GNOME custom keyboard shortcut relies on this.
- **Widget cost:** on Linux, `ResonanceApp` turns off Tk's X input methods (`tk useinputmethods 0`). With them on, Tk registers every window it creates with ibus, which cost about 40ms a window here, so pages took seconds to open and drew line by line. Typing still works (accented letters included); only compose sequences and non-Latin input methods are lost. Even so, customtkinter widgets are two or three windows each, so build a page's widgets once and refill them, reuse a fixed pool when the count varies (the launcher's suggestion rows, the hub's trail crumbs), and draw text-heavy content with `rich_text.RichText` (formatted, clickable rows in one `tk.Text`) or `rich_text.ChipCanvas` (wrapping tag chips on one canvas). Avoid `CTkTextbox` and `CTkScrollbar` (and so `CTkScrollableFrame`): a CTkScrollbar's draw runs `update_idletasks`, a layout pass of the whole window, and a textbox always creates two of them; use `rich_text.TextField` for multi-line input and `line_scrollbar.LineScrollbar` (a 1px rule with an ink thumb, used by the calendar) for a scrollbar. Never reconfigure a Tk font that hasn't changed (use `rich_text.set_font`): any font change makes Tk re-measure every widget in the app. The plain Tk widgets follow the theme and scaling rules below by hand; pack them with `rich_text.scaled_pad`, because CTk only scales the padding of its own widgets. To time a view, measure from the call to after `update()`; the Python side is usually a small part of it.
- **1px lines:** a `CTkFrame(height=1)` draws nothing, so use `windows.add_rule`, which uses a plain `tk.Frame`.
- **Hub layout and full screen:** everything in the hub lives in `hub.content`, a fixed-size frame (`HUB_SIZE`) that is packed to fill the window normally. In full screen it's placed centred over `hub.backdrop`, a `Starfield` created first so it stacks underneath. Parent new hub widgets to `self.content`; panels that need the window itself (the launcher's dropdown, calendar dialogs) use `winfo_toplevel()`. A window that starts non-resizable must be made resizable and `update_idletasks()` run *before* `-fullscreen` is requested, or GNOME ignores the request. Esc in the launcher only clears text; on an empty prompt it falls through to the hub, which leaves full screen. The hub is resizable with `minsize(HUB_SIZE)`, so the title bar has a maximize button. `on_configure` turns maximize into full screen, and any window bigger than the content gets the centred layout too (`apply_layout`: normal, expanded or idle). In full screen, `check_activity` polls the pointer, and key, button and wheel releases count as activity. After `IDLE_AFTER_S` (45s) untouched, `idle_view.IdleView` (a big 24-hour HH:MM:SS clock that ticks on the second, plus the song if playing) replaces the content and the cursor hides. The first Esc while idle only wakes it.
- **Hub apps and pages:** the `≡` button at the top left of the hub opens a menu (`app.show_menu_at`, reusing the right-click menu) listing home plus every hub app; the header shows `t1ld3 / <app>` while an app is open, and clicking the name goes home. Apps with views of their own extend that trail with `hub.set_trail(page, parts)`; clicking a crumb calls the page's `go_to_trail(depth)`. Long trails fold their early middle crumbs into `…` and shorten the one before last (`TRAIL_CHARS`, measured to clear the account name). Home (`home_page.HomePage`: the today briefing, `now_playing_panel.NowPlayingPanel`, weather and to-dos) is built with the hub. Every other page is an app: a module in `resonance/apps/` that defines `APP = HubApp(name, build, order, description)`. `apps.discover()` finds them by scanning the folder, so adding `apps/<name>.py` is all it takes, and a module that fails to import is skipped with a traceback rather than breaking the hub. `build(parent, app)` runs on the first visit. Pages can define optional hooks, which `HubWindow.call_pages` calls when they exist: `on_show`, `data_changed(kinds)`, `show_song`/`show_song_error`/`set_album_art` and `refresh_outlines` (see the docstring in `apps/__init__.py`). Don't reach into a page's widgets from `app.py` or the launcher; add a hook or go through the data layer instead. A panel can appear both on home and in an app (weather, to-do), so each copy must stay in sync by itself: `TodoPanel` listens to `TASKS`, and `WeatherPanel.reload` runs `on_show`. App names also show up as launcher suggestions (kind `"page"`), unless a built-in has the same name. The launcher stays above the pages, and its dropdown must be re-`lift()`ed after a page is packed. PyInstaller can't see modules that are only found by scanning, so both release builds pass `--collect-submodules resonance.apps`; without it the frozen menu is empty.
- **Now playing:** `now_playing_panel.NowPlayingPanel` (home and the music app) draws progress, and on the music page volume, as `TextMeter`s: text bars like the battery's, where clicking a cell seeks (`app.seek`) or sets the volume (`app.change_volume`). Progress counts on between Spotify polls.
- **Calendar:** `events.py` handles local events in `events.json`. It's named `events`, not `calendar`, to stay clear of the stdlib module. It also has time/date parsing and `assign_lanes` for placing overlapping events side by side. `calendar_page.py` draws its views on plain `tk.Canvas`es, because a week of hour slots would be hundreds of CTk widgets. CTk doesn't scale canvases, so every size is multiplied by `ScalingTracker.get_widget_scaling` by hand, including fonts (`tkfont.Font(size=-px)`). Canvas items carry `event:<id>` and `goto:<date>` tags for click handling. `event_dialog.py` holds the add/edit dialog, and only one is open at a time.
- **Right-click menu:** both windows bind `<Button-3>` and call `app.show_context_menu(owner, event, items)` with a list of `menu.MenuItem`s, plus `menu.SIZE_ROW` for the size picker. The app keeps at most one menu open. The actions used by both windows live on the app: `set_size`, `show_about` (`about.py`), `check_for_updates`/the update flow, and `open_spotify`. Dialogs are parented to the window that asked, falling back to any open window (`dialog_parent`). Items with a `detail` are drawn as rows of one `RichText`, with the detail on the right; the hub's `≡` menu uses that for each app's description, and an item's `key` (1–9 there) picks it while the menu is open.
- **Accounts and sync:** Supabase, with email and password, invite-only (sign-ups are off in the dashboard). `cloud.py` is a small urllib client: GoTrue auth, a session in `session.json` that refreshes itself, and pushing and pulling the `items` table. `supabase/schema.sql` defines that one table for every synced kind (`task`, `event`, `setting`, `commands`, `profile`). Its trigger enforces last-write-wins and sets `server_updated_at`, and row-level security limits users to their own rows. The publishable key in `constants.py` is public by design; never put the service_role key in the app.
- **Local-first store:** `store.Collection` keeps one JSON file per kind (`{"version": 2, "records": {id: {data, updated_at, deleted, dirty}}}`), and older plain files convert on load. Always edit through `put`/`delete`, which stamp the time, mark the record dirty and notify the sync engine. Deletes are kept as tombstones. `todo.py`, `events.py`, `settings.py` (synced settings, plus device-only `device.json`) and `user_profile.py` are thin layers over their collections. The profile picture syncs inside the profile record as a 96px greyscale PNG (base64). Each device renders it with `ascii_art.render_avatar` (glyphs, no figure) and `render_avatar_icon` (a Bayer-dithered pixel icon for the header), cached in `app.avatar_images()`.
- **`sync.py` (`SyncEngine`, `app.sync`)** pushes dirty records, then pulls rows with `server_updated_at >=` the stored cursor (an inclusive cursor with offset paging, because batch uploads share a timestamp). It merges by `updated_at` and calls `app.data_changed(kinds)` so panels can `reload()`. It runs 2s after an edit, every 60s and on sign-in. On the first sign-in on a device, everything local is marked dirty so it uploads. A different account signing in clears local data, after asking. Launcher commands sync as a whole file per platform, dated by mtime: pulled files get their mtime set to the remote edit time, and fresh defaults are dated 1970, so synced commands always win and nothing bounces back and forth.
- **Scaling is app-wide.** Each `APP_SIZES` preset is multiplied by `UI_SCALE`: 4/3 on Linux, where Tk ignores the desktop's display scaling, and 1 on Windows, where customtkinter already follows it. `create_app` applies the `DEFAULT_SIZE` zoom before any window exists. `customtkinter.set_widget_scaling` affects every window, so `app.set_size` stores the choice on `app.size_name` and tells the open windows (`player.apply_size`, `hub.refresh_outlines`). Give CTk sizes in unscaled units; CTk scales window sizes but not screen positions.
- **Cookbook:** `recipes.py` holds the data, with no UI code: the `recipe` collection (`recipes.json`), parsing ingredient lines into amount, unit and name (`Ingredient.parse`: "1 1/2 tbsp", "½", "2-3 cloves", "200g", or no number at all), and scaling between the `SERVING_CHOICES` (1 and 2). Amounts are `Fraction`s, stored as strings. Metric amounts round to plain numbers (to 5 from 100 up, with halves rounding up), others to kitchen fractions (`NICE_FRACTIONS`), and the noun's plural follows the new amount. `step_timer` finds the first duration in a step (the shorter one in a range). `cookbook_page.py` holds the app's views: home (favourites, recently cooked, tag chips grouped by `CUISINES`), the filtered list, one recipe, cooking mode (one step at a time, with "you'll need" ingredients matched from the step's words) and the editor. Each view is built the first time it opens and refilled after that (`build_<view>` and `show_<view>`/`fill_<view>`). The page listens to `RECIPES` but doesn't refill the editor or cooking mode. Timers belong to the page, so they keep running while you look elsewhere, and they notify through `app.notify(..., phone=True)` (the same path as reminders, plus a push to the phone app). Cooking mode's arrow and space keys are bound on the hub with `add="+"` and ignore keys typed into an `Entry` or `Text`. Recipes sync like everything else, but `sync.py` uploads them on their own (`NEWER_KINDS`): a server that hasn't run the latest `supabase/schema.sql` rejects only them (they stay dirty, and the account dialog says they're waiting) instead of blocking the whole sync. Keep that for any new kind.
- **To-do:** `todo.py` wraps the synced `task` collection (`todo.json`) and `todo_panel.py` holds the panel used on home and in the to-do app. The launcher's `todo <task>` calls `todo.add_task` directly; every panel re-renders through its `TASKS` listener. The to-do app's copy is `detailed`: it counts what's left and done and lists done tasks under their own heading.
- **Theme:** `assets/terminal_theme.json` must define every key customtkinter reads, for every widget type, or that widget crashes when created (a missing `CTkScrollbar.border_spacing` broke `CTkScrollableFrame`). When adding a widget type, compare against `customtkinter/assets/themes/blue.json`.
- **`constants.py`** holds `APP_VERSION`, repo/release URLs, `APP_SIZES` (window geometry + scaling per size preset), and loads `assets/quotes.json` at import (must be a JSON list of strings).
- **`updater.py`** handles self-update for the Windows `.exe` only: it fetches the latest GitHub release, downloads `t1ld3.exe` (falling back to `Resonance.exe` for releases from before the rename), and writes a `.bat` that swaps the executable after the app exits.
- Assets are resolved via `Path(__file__).resolve().parents[1] / "assets"`, which is why the PyInstaller build bundles them into an `assets` folder.

- **Phone app (`phone/`):** a home-screen web app (PWA) for iPhone: to-dos, the calendar and the cookbook, signed into the same Supabase account. Plain JS modules with no build step, served from GitHub Pages at https://t1ld3.kaylamc.uk by `.github/workflows/phone.yml`; `phone/README.md` has the one-time setup and how it fits together. It mirrors the desktop's data layer: `js/store.js` is `store.py` + `sync.py` (localStorage, last write wins, tombstones, recipes pushed on their own), and `js/recipes.js` is a port of `recipes.py`. **When you change `recipes.py`, change `phone/js/recipes.js` the same way** and run `node phone/tests/parity.mjs`, which runs both on the same inputs. Records must keep the desktop's shapes (`todo.py`, `events.py`, `recipe_data`, settings as `{value}`). iOS home-screen apps can't schedule notifications, so all of them are web pushes from `supabase/functions`: `push` (POST {title, body} with the user's token: the desktop's `cloud.send_to_phone`, used by finished cooking timers and the `phone` command) and `reminders` (run every minute by `supabase/cron.sql`: due event reminders in each phone's time zone, using `_shared/reminders.js`, a port of `reminders.py` tested by `phone/tests/reminders.mjs`, plus the phone's cooking timers from `scheduled_pushes`). `reminders` uses the service role key from the function's own environment; it never goes in the desktop or phone app. The phone's `?api=` test override only works on localhost. `js/gestures.js` handles touch (edge swipe back, swipeable rows, step swipes, pull to sync); each touch is claimed by one gesture once its direction is clear, so add new gestures there rather than with separate touch listeners. New files must be added to `SHELL` in `phone/sw.js`, or the app breaks offline.

## Release process

`.github/workflows/release.yml` runs when a PR is merged into `main`. It bumps the patch version, commits and tags it, builds `t1ld3.exe` on Windows, and attaches it to a GitHub Release. A second job then builds `t1ld3-linux` from the same tag (passed as a job output) and adds it to that release. It also attaches a copy named `Resonance.exe`, because installed pre-rename copies only look for that name when updating; keep it until old installs are gone. Don't bump `APP_VERSION` manually for normal releases.
